## 运行时补充

- 当前状态：已确认首个分歧并完成真实请求二跳验证
- 目标链路 / 函数：`BeginObserver` → collector → `SentinelObserver.Snapshot`

## Official image upload investigation (2026-09-16)

- Target: the current ChatGPT website attachment upload flow, compared with CPA's `POST /backend-api/files`.
- Trigger: one user-approved upload of a generated 16x16 solid-color PNG; no prompt submission or generation.
- Current sample state: one normal website upload completed; the production failure samples remain separate.
- Production evidence: `file_sign` returned 404 or 451; one retained 451 response was `{"detail":{}}` (13 bytes). This does not prove an endpoint change.
- Complexity: L1, request-boundary comparison without challenge or SDK reverse engineering.
- Current stage: validation.
- Why this stage now: the live initialization, binary transfer and completion chain is captured and ready for comparison with CPA.
- Read now: `references/equivalence-and-validation.md`; transition: `references/stage-handoff-protocol.md`.
- Required artifact: `reverse-records/请求链路.md`.

- Sensitive data policy: no access tokens, cookies, file IDs, signed URLs or private file contents in this record.

### Upload stage handoff

- From: locate. To: validation.
- Proven: the official page uploaded the 86-byte PNG through the three requests below, without sending a chat message.
- Write boundary: browser request capture; the transport initiator is the current `4813494d-k4tqhmof689yx2je.js` asset, with the binary uploader in `conversation-small-cyhg2evird2sa17j.js`.
- Open: whether the legacy confirmation endpoint remains supported, whether optional library settings select the new flow, and what caused the production initialization 404/451.
- Invalidated assumption: the observed production 404/451 does not establish that `POST /backend-api/files` was removed.

### Confirmed upload request chain

| Step | Official browser request | Status | Downstream use |
|---|---|---|---|
| Initialize | `POST https://chatgpt.com/backend-api/files` | 200 | Returns `file_id` and a signed `upload_url` |
| Binary upload | `PUT` to the returned `oaiusercontent.com` URL | 201 | Uploads the generated PNG bytes |
| Process/confirm | `POST /backend-api/files/process_upload_stream` | 200 | Returns processing events through completion |

- Initialization body: `file_name`, `file_size`, `use_case: multimodal`, `timezone_offset_min: -480`, `reset_rate_limits: false`, `supports_direct_azure_multipart: true`, `mime_type: image/png`, `entry_surface: chat_composer`, `selection_method: file_picker`, `client_resolved_mime_type: image/png`, `mime_resolution_source: filename_extension`, `store_in_library: true`, `library_persistence_mode: opportunistic`.
- The captured initialization did not send width or height. This does not prove existing width/height fields are rejected.
- Binary headers include `Content-Type`, `x-ms-blob-type`, and `x-ms-version`; the storage URL is taken from the initialization response, never constructed.
- Processing body: `file_id` from initialization, `use_case: multimodal`, `index_for_retrieval: false`, `file_name`, `library_persistence_mode: opportunistic`, `entry_surface: chat_composer`, and metadata with `store_in_library: true`, `is_temporary_chat: false`, `library_eligibility_reason: eligible`, `is_project_thread: false`.
- Processing response Content-Type is `text/event-stream`, but this sample contains newline-separated JSON objects without `data:` prefixes.
- Observed event order: `file.processing.started`, `file.processing.file_ready`, `file.processing.completed`.
- Additional browser GETs after processing: `/backend-api/files/{file_id}/simple`, `/backend-api/files/download/{file_id}`, and an estuary content preview.
- Values tied to the session or resource are intentionally omitted. Only the synthetic filename, harmless MIME metadata, public paths and event names are retained.

### Upload comparison and limits

| Checkpoint | Official browser | Current CPA | Conclusion |
|---|---|---|---|
| Initialization endpoint | `/backend-api/files` | Same | The endpoint is demonstrably still in use |
| Initialization fields | MIME, upload-surface and library metadata | Filename, size, use case, dimensions | Fields differ; one successful sample does not establish which additions are mandatory |
| Binary transfer | PUT to returned signed URL | Same | Protocol shape matches |
| Completion | `/files/process_upload_stream` with explicit events | `/files/{file_id}/uploaded` with empty JSON | Current website flow differs; legacy endpoint retirement is unproven |
| Library persistence | Enabled by the current normal-chat composer | Not explicitly requested | Do not copy persistence settings blindly into temporary reference uploads |
| Production failure stage | Initialization failed before upload | `file_sign` 404/451 | A change in the later completion call cannot by itself explain these earlier failures |
